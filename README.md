# Мессенджер

Учебный проект мессенджера: TypeScript + Vite + Handlebars + PostCSS.
Спринт 4: Безопасность и эксплуатация.

## Команды

- `npm install` — установка зависимостей
- `npm run dev` — dev-сервер на http://localhost:3000
- `npm run build` — проверка типов и сборка в `dist`
- `npm run start` — сборка и запуск `vite preview` на 3000 порту
- `npm test` — тесты (Vitest)
- `npm run test:watch` — тесты в режиме наблюдения
- `npm run lint` — ESLint
- `npm run lint:styles` — Stylelint

## Страницы

| Путь | Страница | Доступ |
|------|----------|--------|
| `/` | Вход | только без авторизации |
| `/sign-up` | Регистрация | только без авторизации |
| `/messenger` | Чаты | только с авторизацией |
| `/settings` | Настройки профиля | только с авторизацией |
| `/404` | Не найдено | всем |
| `/500` | Ошибка сервера | всем |

Неавторизованного пользователя роутер отправляет на `/`, авторизованного со входа и регистрации — в `/messenger`. Неизвестный адрес показывает страницу 404.

При обновлении страницы пользователь остаётся на том же адресе. Открытый чат хранится в адресе (`/messenger?chat=12`), поэтому после F5 он открывается снова вместе с историей сообщений.

## API

Приложение работает с [API Практикума](https://ya-praktikum.tech/api/v2/swagger/#/): регистрация, вход и выход; изменение профиля, аватара и пароля; список чатов, поиск по названию, создание и удаление чата, добавление и удаление участников.

Сессия хранится в куках, поэтому все запросы отправляются с `withCredentials`. Адрес API можно переопределить переменной `VITE_API_URL` в `.env`.

## Чат в реальном времени

При открытии чата приложение получает токен (`POST /chats/token/{id}`) и подключается к `wss://ya-praktikum.tech/ws/chats/{userId}/{chatId}/{token}`.

- Сразу запрашиваются последние 20 сообщений (`get old`), кнопка «Показать более ранние сообщения» подгружает следующие порции.
- Новые сообщения приходят всем участникам без перезагрузки, превью в списке чатов обновляется.
- История хранится на сервере: после перезагрузки страницы и при переключении между чатами сообщения загружаются заново.
- Одновременно открыт один сокет — для активного чата. Он закрывается при смене чата, удалении чата и выходе.
- Каждые 30 секунд уходит `ping`. При обрыве соединения приложение делает до трёх попыток переподключиться.

## Обработка ошибок связи

- **HTTP:** сетевая ошибка, таймаут и ответы сервера приходят как `HTTPError`. 401 отправляет на вход, 5xx — на страницу 500, остальные ошибки показываются под формой.
- **Что видит пользователь:** текст ошибки с сервера (`reason`) на экран напрямую не выводится — в нём могут быть внутренние подробности. Известные ответы переводятся по белому списку (`controllers/errors.ts`), для остальных показывается общий текст по коду ответа. На странице показываются только ошибки `UserError`, тексты которых пишем мы сами; любой другой сбой — «Что-то пошло не так». Подробности пишутся в консоль только в режиме разработки.
- **Запуск:** если сервер недоступен, приложение показывает страницу 500 с кнопкой «Попробовать снова», а не форму входа: недоступный сервер не значит, что сессии нет.
- **WebSocket:** при обрыве над лентой появляется «переподключаемся», после трёх неудачных попыток — «Нет связи с чатом» и кнопка «Повторить». Загруженные сообщения остаются на экране, а недописанный текст не теряется. Когда возвращается сеть (событие `online`), приложение подключается заново.

## Защита от XSS

- Все данные выводятся через `{{ }}` Handlebars, который экранирует HTML. Тройные скобки `{{{ }}}` используются только для вставки компонентов.
- Ошибки и статусы под формами выводятся через `textContent`.
- Адреса картинок из ответов API проверяются: `javascript:`, чужие домены и `..` отбрасываются (`getResourceUrl`).
- Content Security Policy в `index.html` и заголовках Netlify: встроенные скрипты и обработчики вроде `onerror` не выполняются, запросы уходят только на свой сайт и API. `'unsafe-eval'` разрешён, потому что `Handlebars.compile` собирает шаблоны через `new Function`.

## Архитектура (MVC)

```
src/
  core/          Block, registerComponent, Router и Route, HTTPTransport, WSTransport, EventBus, Store
  api/           Model: запросы к серверу — AuthAPI, UserAPI, ChatsAPI
  models/        Model: типы данных и экземпляр Store с состоянием приложения
  controllers/   Controller: AuthController, UserController, ChatController, MessagesController
  components/    View: Button, Input, Field, Avatar, Link, ChatItem, Message
  pages/         View: страницы, наследники Block
  utils/         валидация, формы, queryString, форматирование дат, renderDOM
  styles/        переменные и базовые стили
  router.ts      экземпляр роутера и список адресов
  main.ts        точка входа: регистрация маршрутов и проверка сессии
```

Каждый компонент и страница лежат в своей папке в одном формате: класс `.ts`, шаблон `.hbs`, стили `.pcss` и `index.ts` с экспортом.

Поток данных: страница вызывает контроллер → контроллер делает запрос через API и кладёт ответ в Store → страница подписана на Store и перерисовывается через `setProps`.

Контроллеры не вызывают друг друга напрямую. Например, `ChatController` только меняет активный чат в Store, а `MessagesController.watch()` (запускается в `main.ts`) следит за Store: открывает сокет нужного чата и закрывает его при смене чата или выходе.

### Роутер

`Router` — синглтон по образцу из уроков: `use(path, Page, access)`, `start()`, `go()`, `back()`, `forward()`. История браузера работает через `pushState` и `popstate`, поэтому кнопки «Назад» и «Вперёд» и перезагрузка страницы показывают ту же страницу.

При переходе прошлая страница удаляется из DOM (`Route.leave` → `Block.destroy`), снимаются её обработчики и подписка на Store. Ссылки между страницами — компонент `Link`, который переходит через роутер без перезагрузки.

### HTTPTransport

Обёртка над `XMLHttpRequest` на промисах, без `fetch`. Методы `get`, `post`, `put`, `delete`. Для `GET` данные превращаются в query string (`utils/queryString.ts`), для остальных методов отправляются в теле: объект — как JSON, `FormData` — как есть (загрузка аватара). Ошибка сервера приходит как `HTTPError` со статусом и текстом из поля `reason`.

Общая обработка ошибок в `controllers/errors.ts`: ответ 401 отправляет на вход, 5xx — на страницу 500, остальные ошибки показываются под формой.

### Компоненты

Компонент наследуется от `Block` и регистрируется как Handlebars-хелпер. В шаблоне он вызывается так: `{{{ Button text="Войти" type="submit" }}}`. Внутри `{{#each}}` можно передать текущий элемент целиком: `{{{ ChatItem this }}}`.

Жизненный цикл: `componentDidMount`, `componentWillUnmount`. Вызов `setProps` обновляет props и перерисовывает компонент. События задаются в поле `events` и навешиваются на корневой элемент компонента.

### Формы и валидация

- Правила на регулярных выражениях описаны один раз в `utils/validation.ts` и используются во всех формах.
- Поле проверяется на `blur`, вся форма — на `submit`.
- При отправке страница не перезагружается (`preventDefault`), а в консоль выводится объект со всеми полями формы.
- Ошибки сервера и подтверждения выводятся под формой через `textContent`.
